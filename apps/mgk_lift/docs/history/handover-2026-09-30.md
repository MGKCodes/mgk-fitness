## Working in this repo

**Tests and analysis.** Run from `apps/mgk_lift`:
- `flutter analyze`
- `flutter test`: the whole suite, about a minute.

Run's tests only need re-running when `packages/` changes.

**The screen board.** It is three steps, run from `apps/mgk_lift`:

```bash
flutter build web -t lib/preview/main.dart --release
PLAYWRIGHT_DIR='C:/…/boardtools' node tool/capture_screens_web.mjs
SHARP_DIR='C:/…/boardtools' CAPTURE_DATE=YYYY-MM-DD node tool/build_screen_board.mjs
```

- Then republish `screenshots/screen-board.html` to the board's URL.
- `boardtools` is any folder where `npm install playwright sharp` and
  `npx playwright install chromium` have run. The last one sat in the previous
  session's temp scratchpad and will be gone, so install again.
- **Use Windows-style paths in those variables.** Node reads a Git Bash
  `/c/Users/…` path as `C:\c\Users\…`, and fails with "Could not resolve".
- The builder refuses to run when `lib/preview/main.dart` and
  `tool/screen_board.json` disagree about which screens exist. A new screen
  needs a plate *and* an entry.
- Set `previous`, `since`, and the `new`/`first` tags in the JSON for each new
  round.

**Legal copy.**
- The in-app copy (`legal_copy.dart`), `docs/*.md` and the web pages must agree;
  `test/legal/legal_copy_test.dart` enforces it.
- After editing a legal doc, run `python tool/build_legal_pages.py` from
  `apps/mgk_lift`.

**Design guards.**
- `test/design/raw_buttons_test.dart` forbids raw Material buttons outside
  `mgk_ui`.
- `mgk_ui` changes are welcome from this lane; verify Run's suite afterwards
  (memory `shared-ui-changes-from-an-app-lane`).

**Commits** end with the attribution line in the conversation's system reminder.
Doc style: a ticked item says what landed, and anything settled differently
from the plan says so and why.

**Gotchas from the last session.**
- **Bash heredocs with apostrophes fail** in the Bash tool, with "unexpected EOF
  while looking for matching quote". Write the script to a file with the Write
  tool, then run it.
- **A Codemagic "Publishing failed" can be a successful upload.** Apple returned
  500s mid-upload, altool retried and printed `UPLOAD SUCCEEDED`, and Codemagic
  judged on the error lines. Read the step log before re-running.
- **The emulator's cold start takes over 6 seconds.** Wait before the first
  screenshot.
- **Auto mode also refuses `select` on `auth.users`.** Edge Function deploys,
  function downloads and catalog reads go through.

## Open questions the plan has to answer

These come from the review; Matthew hasn't answered them yet.

1. **Track's layout.** How does one screen hold an unplanned start and today's
   planned session (findings 2 and 17)? Which numbers earn the big tiles?
2. **The builder (W5).** Is it removed entirely, or kept for editing an existing
   workout (W17)?
3. **Save at Finish (12).** Does this replace the automatic learning (D1)
   completely? What does a session that *removed* a movement from its workout do
   now? The review only asks about added movements.
4. **Premade workouts (5).** How much of the catalogue survives, and how does the
   coach offer a workout, for free and paid users?
5. **The C for unsubscribed people (15).** What stays free on the coach, if
   anything? Today the free half has no coach at all. Is the paywall still on
   Plan and Photos, or only behind the C?
6. **Exercise stats (18).** Is a per-exercise screen, where bests move to, in
   this release?
7. **Sign in with Apple and Google (1).** In 2.0.0 or after? It needs a new
   provisioning profile and Supabase and Google Cloud configuration.
8. **Order.** Which findings block submission and which can ship in 2.0.x?
